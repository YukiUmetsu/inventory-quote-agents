# Design Notes and Reflection

## Architecture and Design Decisions

I implemented the system as a five-agent workflow using PydanticAI:

1. **Orchestrator Agent** – coordinates the overall workflow and delegates work to the other agents.
2. **Inventory Agent** – checks whether requested products exist, verifies current stock, determines shortages, and evaluates whether missing inventory can be replenished before the customer's deadline.
3. **Commercial Agent** – generates quotes and finalizes accepted sales.
4. **Customer Agent** – simulates the customer's response to a quote and supports limited negotiation.
5. **Business Advisor Agent** – analyzes internal inventory and financial information and provides operational recommendations.

I chose this architecture because each agent has a distinct responsibility. The Orchestrator controls the process rather than allowing agents to call each other freely. This makes the workflow easier to reason about and helps prevent duplicated inventory checks, repeated sales, or excessive negotiation.

The typical workflow is:

Customer Request
- Inventory Agent
- Commercial Agent for quote
- Customer Agent
- Commercial Agent for sale if accepted
- optional Business Advisor analysis

If the Inventory Agent determines that the complete order cannot be fulfilled, the workflow stops before quoting or creating transactions.

I also used shared request state to track information such as the request date, delivery deadline, quote rounds, customer negotiation rounds, quoted items, and whether a sale was completed.
This helps prevent repeated operations and allows the final sale to use the authoritative quote rather than allowing the language model to invent prices.

The agent tools combine the starter helper functions with business rules.
I kept the tools specific to each agent instead of giving every agent access to every helper function.
The Inventory Agent only has tools for checking whether an order can be fulfilled, while the Commercial Agent handles quoting and sales.
The Business Advisor can read financial and inventory information, but it does not create transactions.
The Customer Agent does not need business tools because its job is only to evaluate the quote.
The Orchestrator's tools are limited to delegating work to the other agents.

I chose PydanticAI because it let me define the agents and their tools using normal typed Python functions without adding much framework-specific structure.
RunContext also gave me a straightforward way to pass request state to the agents that need it, and UsageLimits let me put limits on how many model requests each agent can make.
This fit the project well because I wanted the LLMs to handle interpretation and coordination while keeping inventory, pricing, and transaction logic in regular Python code.

For example, inventory checks use stock levels, supplier delivery dates, and available cash, while quote generation applies a deterministic bulk-discount policy and consults historical quote data when available.


## Evaluation Results

I evaluated the system using the full `quote_requests_sample.csv`
dataset containing 20 customer requests.

In the final test run:

- **6 requests were successfully fulfilled**
- **6 requests resulted in a change to the cash balance**
- **14 requests were not fulfilled**
- Every unfulfilled request included an explanation of why the complete
  order could not be processed

The fulfilled requests were requests 1, 4, 5, 6, 10, and 12.

Successful orders included both items that were already in stock and items that had to be replenished before the customer's deadline.

Rejected requests included several different cases:

- products that were not in the company catalog
- insufficient stock that could not be replenished before the required
  delivery date
- supplier replenishment that would arrive after the customer's deadline
- composite orders where only some of the requested products could be
  supplied

During testing, requests that failed the inventory check stopped before quoting, while feasible requests continued through quoting, customer evaluation, and sales.

Most successful requests required one quote and one customer evaluation. Request 10 was different: it went through two quote rounds and two customer rounds before the quote was accepted.

The final run fulfilled six requests and changed the cash balance on six requests. The other fourteen were rejected when the full order could not be completed.

## Strengths

I kept the important business calculations outside the LLM. Stock levels, supplier dates, prices, and transactions come from Python functions and database data. The agents mainly interpret customer requests and coordinate those tools.

Quote prices are also deterministic. The Commercial Agent uses catalog prices, a fixed bulk-discount rule, and historical quote data instead of making up a price.

The shared request state also prevents duplicate work. Inventory is checked once per request, a sale can only be finalized after the quote is accepted, and the sale uses the quantities and prices saved from that quote. 

Customer-facing responses generally explain why an order succeeds or fails without exposing internal cash balances, profit information, database details, or transaction IDs.

The Customer Agent also adds a negotiation step based on the customer's request context, which makes the workflow more realistic than automatically accepting every generated quote.

## Areas for Improvement

### 1. Profitability-aware pricing

The current quote policy applies deterministic bulk discounts based
primarily on order quantity. In the final evaluation, some successfully
fulfilled orders produced a negative request-level cash change because
the cost of replenishing inventory exceeded the revenue collected from
the discounted sale.

A future version should consider procurement cost when generating a
quote and enforce a minimum contribution margin before applying a bulk
discount. This would prevent feasible orders from being accepted at
prices that are operationally unprofitable.

### 2. Product substitutions

The current workflow rejects the complete order when a required product
is unsupported or cannot meet the delivery deadline.

I would also like to add product substitutions.
If an exact item is unavailable, the system could offer a similar catalog item and let the Customer Agent decide whether it is acceptable.
For example, the system could suggest a supported paper size or paper type rather
than immediately rejecting an order containing an unsupported product.

### 3. More structured agent outputs

The business-critical calculations and tool inputs are structured and
deterministic, but agent responses and some orchestration decisions are
still expressed as natural language.

A future version could use Pydantic response models for agent-to-agent
outputs such as inventory decisions, quote decisions, customer negotiation
responses, and final sale summaries. This would reduce reliance on parsing
natural-language responses and make the workflow easier to validate
automatically.

### 4. More detailed fulfillment and accounting state

The starter transaction model uses a relatively simple representation
of stock purchases and sales. A production system should separately
track purchase date, supplier arrival date, customer order date,
fulfillment date, and delivery date.

Separating these concepts would provide more accurate inventory and
cash-flow accounting.

## Conclusion

The agents handle interpretation and coordination, while Python tools handle inventory, pricing, and transactions.

In the final test run, feasible orders were completed and orders with unsupported products or impossible deadlines were stopped before a sale was recorded.
If I continued the project, I would focus next on profitability-aware pricing, product substitutions, and more structured agent outputs.
